Glanzow

A Mac menu bar app that watches which screen you're facing through the camera, and moves keyboard focus there before you type: to the screen, the window, and the split pane you're looking at.

Built from a 14-page requirements document in one Claude Code session.

What was built

The spec described the app in six milestones. Each one ended with a working build and passing tests before the next began.

The app

  • Finds your face 15 times a second with Apple's Vision framework and smooths out the jitter.
  • Learns your screens in a 20-second calibration per screen: you follow a moving light.
  • Picks the screen you face, and within it the window or split pane, after a short hold so glances don't count.
  • Never interrupts: it waits while you type, use the mouse, or have a menu, dialog, password field or Mission Control open.
  • Stays on the Mac: frames are never saved, and it makes no network calls.

Around it

  • A four-step welcome window, Settings, and a menu bar icon that shows its state.
  • A replay tool that runs recorded head movements back through the same decision code, for tuning without sitting at the desk.
  • A debug overlay with live head angles, the gaze point and the reason a switch was held back.
  • A README covering building, signing, notarizing (Apple's malware check for apps shipped outside the App Store) and resetting permissions.

Processor use

The spec allows 5% of one processor core on an M1 Mac. Face detection is the expensive step; it was measured here on an M3 Pro, which is faster, so the M1 numbers will be higher.

Share of one core, by tracking mode

Measured as processor time per 1280×720 frame: 1.9–2.3 ms for face detection alone. Eye tracking is what window and pane focus needs; running it on every other frame keeps the default under the budget.

Decisions worth knowing

Where the spec was ambiguous, the rule was to pick whatever switches focus less, and mark the choice in the code. There are 14 such notes and 5 marked shortcuts. These are the ones a user would notice.

The spec's lean-in formula was reversed

Leaning in makes screens look further apart. The spec multiplied by face size, which pushes the wrong way; the app divides.

Nothing to change: the spec's own reasoning supports it.

“Head turn needed” starts at 1.2×

The spec says switching needs “at least 1.2×” the margin, but puts the default at 50%. The slider now runs from 1.2× to 1.6×, so the default is 1.4×.

If switching feels slow, lower the slider.

Any lost frame restarts the wait

A screen must win for 300 ms “continuously”, so a single frame without a face starts the count again.

Revisit if switching feels sluggish in poor light.

Windows wait a little longer than screens

Eye position is noisier than head position, so focus moves within a screen after 450 ms instead of 300 ms, and only once the gaze is clearly inside the new window.

Tied to the screen delay setting: 1.5 times it.

Panes only in terminals and editors

iTerm2, Terminal, VS Code, Xcode, Zed, JetBrains and similar get pane focus. Browsers and chat apps switch whole windows, so a page region never steals focus.

A clicking fallback exists for apps that ignore the request; it is off by default.

Head tilt is filtered, not corrected

Correcting tilt depends on how Apple combines its angles, which isn't documented. Poses tilted over 30° are ignored instead.

One test recording with a tilted head would settle it.

Independent review

Two separate AI agents read the finished code: one hunting bugs, one checking every requirement in the spec against the code.

The most important catch: the app would never have switched focus

The check that waits while Mission Control is open looked for a full-screen window owned by the Dock. On this Mac the Dock always has one, so every switch was blocked. The unit tests couldn't see it because they replace that check with a stand-in. It now uses the signal macOS sends when Mission Control opens and closes.

The checks

  • 50 automated tests across nine areas, from the smoothing filter to the timing of every switch.
  • The smoothing filter matches an independent Python version of the published algorithm to 9 decimal places.
  • A replayed minute of head turns produced 4 correct switches, each 0.333 s after settling. It ignored glances of 0.2 s and 0.25 s, and 3 s spent looking down at a phone.
  • Every screen was rendered and inspected in light and dark mode before shipping: welcome steps, Settings, calibration and the focus flash.
